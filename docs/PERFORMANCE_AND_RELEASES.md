# الأداء والإصدارات في مدار

## رقم الإصدار
- الإصدار = رقم `version` في `package.json` + بصمة كل ملفات `public/` (مثل `2.1.0-658ec830c0`).
- أي تعديل في أي ملف واجهة ينتج بصمة جديدة تلقائيًا. **لا يوجد رقم يُرفع يدويًا.** يُرفع `version` فقط للإصدارات المعلنة.
- يظهر في تذييل كل صفحة، وفي `GET /api/version`، وفي ترويسة `X-App-Version` لكل استجابة API.

## كيف تصل النسخة الجديدة للمستخدمين
1. الصفحات (HTML) لا تُخزَّن أبدًا (`no-cache`)، والخادم يكتب فيها روابط الإصدار الحالي.
2. كل ملفات JS/CSS تُخدم من `/v/<الإصدار>/…` بكاش دائم (`immutable`). الاستيرادات داخل الملفات نسبية، فتنتقل كلها معًا.
3. عامل الخدمة (`/sw.js`) يُولَّد لكل إصدار: يكتشف المتصفح التغيير، ويحذف كاش الإصدار السابق كاملًا.
4. الصفحة المفتوحة وقت النشر: أول استجابة API تكشف الإصدار الجديد ← يظهر شريط «يتوفر إصدار جديد» ←
   يتحدث التطبيق تلقائيًا عند الانتقال بين الأقسام (نقطة آمنة لا تقطع عملًا مفتوحًا).
5. Firebase: `npm run build:hosting` ينشر نسخة `/v/<الإصدار>/shared` على الـ CDN بكاش دائم.

## قبل كل تحديث كبير
1. `npm test` — كل الاختبارات يجب أن تنجح.
2. تجربة الأقسام المعدّلة في المتصفح (الكمبيوتر والجوال).
3. قياس السرعة: ترويسة `Server-Timing` في أدوات المطور تعرض الزمن الكلي وزمن قاعدة البيانات وعدد الاستعلامات لكل طلب.
4. النشر (`npm run migrate` ثم النشر).
5. التحقق: `curl <الرابط>/api/version` يجب أن يعرض الإصدار الجديد، وتذييل الصفحة كذلك بعد فتحها.
6. مراقبة سجل الخادم: كل طلب أبطأ من 400ms يُسجَّل بسطر `[slow]` (يُعدَّل بـ `SLOW_REQUEST_MS`).

## قواعد للحفاظ على السرعة مع نمو البيانات
- لا تُنزَّل قائمة كاملة (طلاب، فواتير…) لملء قائمة اختيار أو لحساب عدد: استخدم `limit` و`summary` و`fields=basic`.
- القوائم الطويلة: صفحات من الخادم (`limit`/`offset` + `X-Total-Count`) وتحميل تدريجي في الواجهة.
- لا دوال لكل صف في استعلام على آلاف الصفوف: تجميع واحد (JOIN + GROUP BY).
- أي استعلام جديد على جدول كبير: `EXPLAIN ANALYZE` قبل الدمج، وفهرس عند الحاجة (مثل 0032).
- الأقسام تُحمّل عند فتحها (`lazy`) — لا استيراد ثابت لأقسام اللوحة في `app.js`.
- الصور: مصغرة للعرض، والأصلية عند الطلب أو الطباعة فقط.
