# خطة الاستجابة للحوادث الأمنية — مدار

تُطبّق عند الاشتباه بالتالي:
- اختراق حساب، أو وصول غير مصرح به لبيانات مدرسة.
- تسريب مفتاح أو كلمة مرور.
- حذف أو تعديل غير مقصود على نطاق واسع.
- تعطل يهدد البيانات.

**المسؤول الأول:** مالك المنصة. وهو من يعيّن نائبًا له، ويسجّل وسيلة التواصل معه في مدير كلمات المرور مع بقية الأسرار.

## مصادر الاكتشاف

| المصدر | أين تراه |
|---|---|
| التنبيهات الأمنية: دخول المالك من جهاز جديد، ومحاولات دخول فاشلة متكررة، وقفل حسابات، وطلبات مرفوضة متكررة من حساب مدرسة، وحذف 50 سجلًا أو أكثر دفعة واحدة، وتصدير نسخة كاملة لمدرسة | لوحة المالك ← «الأمان» (مع صوت وإشعار)، وبالبريد إذا ضُبط `OWNER_ALERT_EMAIL` |
| فشل النسخ الاحتياطي أو اختبار الاسترجاع | بريد GitHub (Actions) |
| توقف الموقع أو قاعدة البيانات | بريد GitHub من «مراقبة الموقع»، وUptimeRobot |
| بلاغ من مدرسة | الدعم |

## الخطوات

### 1. التحديد (خلال 30 دقيقة)
- ما الذي حدث، ومتى بدأ، وأي مدرسة أو حساب متأثر؟
- المصادر:
  - لوحة المالك ← الأمان (التنبيهات والجلسات).
  - لوحة المالك ← سجل العمليات.
  - سجل عمليات المدرسة.
  - سجلات Render (Logs).
- سجّل كل ما تجده بالوقت في ملف الحادث (نموذج في الأسفل).

### 2. الاحتواء (فورًا عند التأكد)

| الموقف | الإجراء |
|---|---|
| اختراق لوحة المالك | الأمان ← «إنهاء كل الجلسات الأخرى»، ثم كلمة مرور جديدة (`npm run owner:password` ثم `OWNER_PASSWORD_HASH` في Render)، ثم أعد ضبط التحقق الثنائي، ثم فعّل `OWNER_ALLOWED_IPS` |
| اختراق حساب مدير مدرسة | ملف المدرسة ← استعادة دخول المدير (ينقل المدرسة لحساب جديد ويقطع القديم)، أو إيقاف المدرسة مؤقتًا |
| اختراق حساب معلم أو محاسب | الإدارة توقف الحساب، أو تعيد كلمة مروره (تنتهي جلساته فورًا) |
| خطر على كل المنصة | Render ← Suspend للخدمة. البيانات تبقى محفوظة في Neon |
| حذف أو تعديل واسع | أوقف الكتابة، ثم اتبع [خطة التعافي](DISASTER_RECOVERY.md) القسم 4 |

### 3. إبطال الأسرار المكشوفة

لا يكفي حذف السر من الملف: يجب تغييره في مصدره ثم تحديثه في Render.

| السر | الإبطال |
|---|---|
| رابط قاعدة البيانات | Neon ← Roles ← Reset password للدور، ثم تحديث `DATABASE_URL` و`MIGRATION_DATABASE_URL` |
| `CREDENTIAL_KEY` | مفتاح جديد (`npm run credential:key`). كلمات المعلمين المؤقتة القديمة تصبح غير مقروءة، والحسابات تعمل، وتُصدر كلمات مؤقتة جديدة عند الحاجة. التحقق الثنائي المفعّل من الشاشة يحتاج إعادة تفعيل |
| `BACKUP_PASSPHRASE` | كلمة جديدة في أسرار GitHub. النسخ القديمة تبقى بكلمتها القديمة؛ احفظ الاثنتين |
| مفاتيح Google/Apple/البريد/الرسائل | من لوحة كل مزود، ثم «الدخول والبريد» أو «الرسائل النصية» في لوحة المالك |
| `OWNER_TOTP_SECRET` | `npm run owner:totp` وضع الناتج في Render، أو امسحه من القاعدة لإعادة التفعيل من الشاشة |

### 4. تحديد الأثر
- **ما الذي قُرئ أو عُدّل:** سجل التدقيق يحفظ القيم قبل التعديل وبعده لكل جدول مراقَب.
- **ما الذي صُدّر:** كل تصدير كامل مسجّل، ويرفع تنبيهًا.
- **من دخل ومن أين:** سجل الدخول في كل مدرسة.

### 5. الاسترجاع
- من نسخة موثوقة حسب [خطة التعافي](DISASTER_RECOVERY.md).
- لاسترجاع مدرسة واحدة: نسخة «منطقة الحذر» أو الفرع الزمني في Neon.

### 6. التحقق قبل إعادة التشغيل
- السبب أُغلق، والأسرار المكشوفة أُبدلت.
- `/healthz/db` يعمل، ودخول المالك بالتحقق الثنائي يعمل.
- اختبار العزل في CI ناجح على آخر نسخة من الكود.

### 7. الإبلاغ والتوثيق
- **إبلاغ المدرسة المتأثرة كتابيًا:** ماذا حدث، ومتى، وأي بيانات تأثرت، وما الذي فعلناه، وما المطلوب منها.
- **الإبلاغ النظامي:** عند انطباق نظام حماية البيانات الشخصية في بلد المدرسة، تُبلَّغ الجهة المختصة خلال المهلة النظامية؛ في السعودية 72 ساعة من العلم بالحادث (سدايا)، مع إشعار أصحاب البيانات عند وجود ضرر. تُراجع المتطلبات مع مستشار قانوني قبل الإطلاق التجاري.
- **ملف الحادث يُحفظ سنة على الأقل:** الخط الزمني، والسبب الجذري، والإجراءات، والدروس المستفادة.

### 8. معالجة السبب الجذري
- إصلاح في الكود مع اختبار يمنع تكرار الثغرة نفسها.
- تحديث هذه الخطة إن لزم.
